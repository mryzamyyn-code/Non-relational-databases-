## 1. Введение

Цель проекта — разработать каталог электроники на основе MongoDB, обеспечивающий хранение товаров, поиск по характеристикам, фильтрацию, сортировку и получение агрегированной информации.

MongoDB выбрана благодаря документной модели хранения данных, поддержке гибких структур документов, индексов и aggregation pipeline. Для взаимодействия с базой используется Python и библиотека PyMongo. База размещена в MongoDB Atlas.

## 2. Постановка задачи

Необходимо разработать систему хранения и поиска информации об электронике. Каталог должен содержать сведения о названии товара, категории, бренде, цене и количестве на складе.

Система должна поддерживать выборку товаров по категории и бренду, поиск по диапазону цен, сортировку по стоимости, проверку остатков и анализ средней цены по категориям.

Для проверки реализации используются синтетические данные. В коллекцию `products` загружено 30 демонстрационных товаров.

## 3. Функциональные требования

1. Система должна подключаться к MongoDB Atlas.
2. Система должна хранить информацию о товарах.
3. Система должна отображать список товаров.
4. Система должна выполнять поиск по категории.
5. Система должна выполнять поиск по бренду.
6. Система должна фильтровать товары по цене.
7. Система должна сортировать товары по цене и остатку.
8. Система должна находить товары по нескольким условиям.
9. Система должна вычислять количество товаров и среднюю цену по категориям.
10. Система должна поддерживать создание индексов для часто используемых запросов.

## 4. Нефункциональные требования

1. Надёжность: при ошибке подключения система должна сообщать об ошибке.
2. Безопасность: строка подключения хранится в локальном файле `.env`, который нельзя публиковать.
3. Поддерживаемость: код разделён на исходные файлы, скрипты и тесты.
4. Расширяемость: структура документов позволяет добавлять новые характеристики товаров.
5. Производительность: индексы должны помогать ускорять типовые запросы. Фактический прирост скорости должен проверяться измерениями.

## 5. Модель данных

Используется база `electronics_catalog` и коллекция `products`.

Пример документа:

```json
{
  "name": "iPhone 16",
  "category": "Смартфоны",
  "brand": "Apple",
  "price": 399000,
  "stock": 12,
  "seed_source": "sro_demo"
}
```

Поля документа:

- `name` — название товара;
- `category` — категория электроники;
- `brand` — производитель;
- `price` — цена в тенге;
- `stock` — количество на складе;
- `seed_source` — метка синтетических записей для демонстрационного заполнения.

Документная модель подходит для каталога, поскольку сведения о товаре хранятся в одном документе и могут расширяться при необходимости.

## 6. Архитектура решения

Приложение состоит из следующих компонентов:

1. Пользователь запускает Python-скрипт.
2. Скрипт считывает строку подключения из `.env`.
3. PyMongo устанавливает соединение с MongoDB Atlas.
4. Запросы выполняются к базе `electronics_catalog`, коллекции `products`.
5. MongoDB возвращает документы или результаты агрегации.
6. Результаты выводятся в терминал.

Схема взаимодействия:

```text
Пользователь
     |
     v
Python-скрипты
     |
     v
PyMongo
     |
     v
MongoDB Atlas
     |
     v
electronics_catalog
     |
     v
products
```

## 8. Индексы и оптимизация запросов

В демонстрационном скрипте создаются следующие индексы:

- составной индекс `category + price`;
- составной индекс `brand + price`;
- текстовый индекс по полю `name`.

Составные индексы ориентированы на запросы, в которых используются соответствующие поля. Текстовый индекс предназначен для текстового поиска по названию.

Наличие индекса само по себе не доказывает ускорение каждого запроса. Для оценки эффективности следует сравнить планы выполнения запросов с помощью `explain("executionStats")` и измерить фактическое время выполнения на достаточно большом наборе данных.

## 9. Сравнение вариантов хранения

**MongoDB.** Документная модель подходит для каталога с изменяемым набором характеристик. Поддерживаются индексы, фильтрация и агрегация.

**Реляционная база данных.** PostgreSQL или MySQL удобны при строгой схеме, сложных связях между сущностями и транзакциях с несколькими связанными таблицами.

**Выбор:** MongoDB, поскольку задача ориентирована на документное хранение каталога и демонстрацию поисковых запросов с использованием индексов.

## 10. ADR — запись архитектурного решения

**Решение:** использовать MongoDB Atlas и PyMongo.

**Контекст:** требуется хранить каталог товаров с гибкой структурой документов и выполнять запросы по нескольким атрибутам.

**Рассмотренные альтернативы:** реляционная база данных MySQL или PostgreSQL.

**Причины выбора:** документная модель, удобный доступ из Python, поддержка индексов и агрегации, облачное размещение базы.

**Компромиссы:** необходимо контролировать согласованность структуры документов, безопасность доступа и стоимость облачного размещения. Для сложных связей между сущностями реляционная модель может быть удобнее.

## 11. Реализация и демонстрационные запросы

Для заполнения базы создан скрипт `scripts/seed_data.py`. Он добавляет 30 синтетических записей в коллекцию `products`.

Скрипт `scripts/demo_queries.py` выполняет восемь групп запросов:

1. Получение первых пяти товаров.
2. Поиск по категории «Смартфоны».
3. Выборка товаров бренда Apple.
4. Поиск товаров дешевле 100 000 тенге.
5. Поиск товаров в диапазоне от 100 000 до 300 000 тенге.
6. Поиск товаров с остатком не менее десяти единиц.
7. Выборка товаров Apple дороже 200 000 тенге с сортировкой по цене.
8. Вычисление количества товаров и средней цены в каждой категории с помощью aggregation pipeline.

При фактическом запуске все восемь групп запросов вернули результаты, а индексы были созданы и проверены.

## 13. Безопасность

Строка подключения хранится в `.env`. Файл с реальными учётными данными нельзя добавлять в репозиторий GitHub.

Для публикации следует подготовить `.env.example` с шаблоном переменной `MONGODB_URI`, не содержащим настоящий пароль. Для пользователя базы данных необходимо выдавать только требуемые права доступа.

## 14. Ограничения проекта

Текущая версия является учебным прототипом. Данные синтетические, а интерфейс представлен Python-скриптами и выводом в терминал. Полноценный веб-интерфейс и нагрузочное тестирование не реализованы.

Эффективность индексов требует отдельного измерения на большем наборе данных. Результаты тестирования относятся к текущему состоянию проекта и могут измениться при модификации кода или данных.
